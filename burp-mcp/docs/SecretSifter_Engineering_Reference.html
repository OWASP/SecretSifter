1. System Overview

What SecretSifter is, what it does, and the full technical scope of what was built.

SecretSifter is a Burp Suite extension (Montoya API) for passive and active detection of exposed secrets in HTTP traffic. It is not a wrapper around an existing scanner — every detection rule, every false-positive guard, every threshold, and every scan phase was written from scratch.

Core Capabilities Built

  • Passive scanning of all proxy traffic (fires on every response, all tiers)
  • Active rescan via context menu (right-click → Rescan for Secrets)
  • Bulk Scan tab: URL list, HAR import, 1–50 threads, webpack chunk following
  • Headless Chrome integration (via Burp proxy for dynamic SPA traffic)
  • Scope Monitor: routes cross-origin proxy findings to the Bulk Scan panel
  • Sitemap sweep on load: scans existing site-map responses retroactively
  • HTML + CSV + per-domain ZIP report export
  • Inline response tab in Proxy History / Repeater
  • Multi-provider AI Triage: Burp AI, Anthropic API, OpenAI/compatible — per-finding + bulk with noise review dialog
  • MCP Bridge: JSON-RPC server on 127.0.0.1:8765 for Claude Code integration
  • Full settings persistence to Burp Preferences (ss.* keys)
  • Two-JAR build: Store (no MCP) and Full (with MCP)

2. Build System & Two-JAR Architecture

Gradle configuration, shadow JAR splits, and the reason for two entry points.

Why Two JARs

PortSwigger BApp Store submission rules prohibit extensions with embedded HTTP listeners or server sockets. The MCP Bridge opens a server socket on 127.0.0.1:8765 for JSON-RPC. To comply with store requirements while shipping the full feature set to direct download users, the build produces two distinct JARs with different entry points:

JAREntry PointMCP BridgeDistribution
secretsifter-store-*.jarSecretScannerExtensionStoreExcluded at build timeBApp Store, community
secretsifter-mcp-*.jarSecretScannerExtensionIncludedGitHub Releases, direct download

Gradle Build Tasks

./gradlew shadowJar       # store JAR  → build/libs/secretsifter-store-*.jar
./gradlew shadowJarFull   # full JAR   → build/libs/secretsifter-mcp-*.jar
./gradlew buildAll        # both JARs
./gradlew test            # JUnit 5 tests

Build Configuration Key Points

  • montoya-api:2026.2 is compileOnly — Burp provides it at runtime; it must NOT be bundled in the shadow JAR
  • gson:2.10.1 is implementation — bundled; used for JSON body walking
  • The shadowJar task uses exclude 'com/secretscanner/McpBridge.class' and exclude 'com/secretscanner/SecretScannerExtension.class' to strip the full-build classes
  • The shadowJarFull task excludes only SecretScannerExtensionStore.class
  • Both JARs are ~430 KB — the size difference is negligible since McpBridge is one class

3. Scan Pipeline — 10 Phases

Every phase that runs when SecretScanner.scanText() is called, in order. All phase methods are private; scanText() is the only public entry point.

Key design invariant: SecretScanner is fully stateless — no mutable fields are written during scanText(). All patterns are compiled once at JVM load in Patterns.java static initializers. Settings are read (not written) via volatile fields or synchronized getters. This makes the scanner safe for concurrent calls from all 50 bulk-scan worker threads simultaneously.

Before phases run, two gates check whether to scan at all:

  1. Content-type gate: binary, image, video, audio, and font responses are skipped entirely.
  2. HTML inline script extraction: if Content-Type is HTML, <script> blocks (without src) and <script type="application/json"> blocks are extracted and recursively scanned as JS/JSON respectively — preventing double-reporting from the outer HTML body.
1
Anchored Token Scan FAST+ 100+ vendor-specific regex patterns with format-anchored prefixes (ghp_, sk-, AKIA, etc.). Near-zero false positive rate because the prefix uniquely identifies the vendor. One regex pass per pattern. Results are CERTAIN confidence.
2
URL Credential Scan FAST+ Three patterns: URL_WITH_CREDS (https://user:pass@host), URL_QUERY_CREDS (?password=X, ≥4 chars), BARE_QUERY_CREDS (relative URL, ≥20 chars). Confidence: FIRM.
3a
DB Connection String Scan LIGHT+ Two patterns: DB_CONN_STRING (mongodb/postgres/mysql/redis/amqp/jdbc URIs with embedded credentials) and DOTNET_CONN_STR (SQL Server semicolon format; guarded against arithmetic expressions). Confidence: FIRM.
3b
Context-Gated Rules LIGHT+ 40+ rules. Each requires a vendor keyword within ~200 chars before the value pattern fires. AWS secret key, Azure DevOps, Snowflake, Algolia, Cloudflare, Auth0, and more. Confidence: FIRM.
4
Generic KV Scanner FULL Matches key=value and key: value pairs where key is a semantic secret name. Uses REAL_SECRET_KEYNAME (100+ key patterns) plus isProbableSecretValue() guard. Also runs form-encoded pre-pass for OAuth token responses. Confidence: TENTATIVE.
5
SSR State Blob Unwrap FULL Detects Next.js __NEXT_DATA__, Nuxt __NUXT__, window.__INITIAL_STATE__, REDUX_STATE, and similar patterns. Extracts the embedded JSON and re-runs the full pipeline against it recursively.
6
High-Entropy Scanner FULL Shannon entropy H = −∑(p_i · log₂(p_i)) applied to quoted strings 20–512 chars. Context keyword required within ±80 chars (±200 for crypto operations in minified JS). Default threshold: 3.5 bits/char. Confidence: TENTATIVE.
7
Getter Function Scanner FULL (JS only) Two patterns: GETTER_ARROW_SHORT (const getKey = () => 'VALUE') and GETTER_FUNC_RETURN (const getKey = function() { return 'VALUE'; }). Catches secrets returned from getter methods that are otherwise invisible to key=value scanners.
8
JSON Deep Walk FULL Uses Gson to parse JSON bodies, then walks the tree depth-first. Depth cap: 20 levels. Finding cap: 50 per response (prevents megabytes of JSON flooding reports). Every leaf string checked against REAL_SECRET_KEYNAME and scored.
9
XML Leaf Scanner LIGHT+ Extracts tag + text content pairs from XML/SOAP responses. Checks tag name against REAL_SECRET_KEYNAME. Catches secrets in SOAP web service responses and XML config endpoints.
10
PII Scanner FULL Two sub-phases: (a) SSN — structural format check with exclusion rules (no 000/666/9xx prefix, no 00 middle, no 0000 suffix) + requires SSN context keyword; (b) Credit card — 13–19 digit candidates validated with Luhn checksum algorithm. Confidence: FIRM.

Additional optional phases always available (all tiers):

  • CryptoJS passphrase scan: CryptoJS.AES.decrypt("cipher","KEY"), CryptoJS.HmacSHA*(data,"KEY")
  • Custom rules: user-defined regex from Settings (runs ALL tiers)
  • Request header scan: opt-in; checks KNOWN_SECRET_HEADERS and semantic key headers

6. Entropy & Generic KV Scanner

How the FULL-tier heuristic scanner works — the part that catches unlisted keys.

Shannon Entropy Formula

H(s) = -∑ p_i · log₂(p_i)   for each unique character in s

where p_i = count(char_i) / len(s)

Default threshold: 3.5 bits/char
Range: 0.0 (all same char) to log₂(charset_size) ≈ 6.0 for random base64

Entropy Scanner Gate Conditions (ALL must pass)

  1. Value is a quoted string 20–512 characters
  2. Value entropy ≥ threshold (default 3.5)
  3. Context keyword within ±80 chars OR key name passes isSemanticSecretKey()
  4. Value is not a UUID (8-4-4-4-12 format) — unless key ends in Secret or Token
  5. Value does not match JWT format
  6. Value is not a placeholder (example, xxxx, changeme, etc.)
  7. Value character composition is not homogeneous (>60% same character = reject)
  8. Key name is not in FORCED_NOISE_KEYS (90+ exact matches)
  9. Key name does not match NOISE_KEYNAMES regex (60+ noise patterns)
  10. Value does not start with JS code fragment patterns (this., ), etc.)

Semantic Key Analysis — isSemanticSecretKey()

A key name must satisfy BOTH conditions:

  • Secret-domain prefix: starts with or contains one of: api, app, auth, secret, private, priv, access, user, account, service, client, oauth, db, database
  • Secret-type suffix: ends with or contains one of: key, token, secret, password, passwd, pwd, credential, cred, pass, hash

Examples: api_key ✓, auth_token ✓, client_secret ✓, alertKey ✗ (no secret-type suffix), key ✗ (no secret-domain prefix)

Generic KV Pattern

# Simplified — actual regex includes quote variants and spacing
(?i)([\w.-]{2,60})\s*[:=]\s*["']([A-Za-z0-9_.+=|?#~@!$%^&*/-]{8,512})["']

Only fires when key passes REAL_SECRET_KEYNAME (100+ key patterns) and value passes isProbableSecretValue(). Confidence: TENTATIVE.

8. JWT Handling Logic

JWT findings are contextual — the same JWT in a response means different things depending on what was in the request.

Request StateJWT in ResponseReported AsRationale
Request has Authorization: Bearer [JWT]SuppressNot reportedNormal authenticated API call — response JWT is likely a refresh or resource ID, not a leaked credential
Request has non-JWT credential header (X-API-Key, etc.)Upgrade to HIGHHIGH / CERTAINPattern matches a token-issuance endpoint — the JWT in the response is the issued token itself
Request is unauthenticated (no credential headers)Report as-isMEDIUM / CERTAINJWT in response of unauthenticated request may be an exposed credential
Any requestJWT in request header directlyMEDIUM / CERTAINJWT in request headers scanned only if request header scanning is enabled

JWT Validation

Pattern: eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}

Additional check: the second segment (eyJ… prefix, base64url-encoded JSON header) must decode to valid JSON-like content. Two-segment values (header.payload without signature) are not reported.

9. Deduplication Architecture

Two completely separate dedup namespaces, each serving a different purpose.

Namespace 1 — Request Value Dedup (seenRequestValues)

  • Type: Collections.synchronizedSet(new HashSet<String>())
  • Scope: Session lifetime (cleared on extension unload)
  • Purpose: Prevents the same hardcoded API key from being reported once for every request that carries it. If a React app sends X-API-Key: sk_live_xxx in 200 requests, the finding is reported once.
  • Used by: Proxy handler path only. NOT used by bulk scan (one-shot, no shared state).
  • Key format: Matched value string (e.g. sk_live_abc123)

Namespace 2 — Sitemap Dedup (SitemapDeduplicator)

  • Type: Two ConcurrentHashMap<String, Boolean> instances — seen (bulk scan) and proxySeen (proxy handler)
  • Scope: Session lifetime (cleared on extension unload)
  • Purpose: Prevents api.siteMap().add() from creating duplicate AuditIssues for the same finding at the same URL
  • Why two maps: If bulk scan and proxy handler share one map, a bulk scan finding for a URL blocks the proxy handler from reporting the same finding when the browser later proxies to that URL at a different location. The split ensures independent dedup per scan path.
  • Bulk scan key format: '\u0001' + normUrl + SEP + ruleName (group dedup) + normUrl + SEP + matchedValue (per-finding dedup)
  • Proxy handler: Uses shouldAddProxy() → writes to proxySeen map only

URL Normalization for Dedup

  • Strip #fragment
  • Strip ?querystring
  • Strip source suffixes: [HTML], [JS], [JSON], [XML], [REQ-HEADERS]

macOS EDT Fix (Sitemap Sweep)

On macOS, api.siteMap().requestResponses() returns an empty list when called from a non-EDT thread (Montoya's macOS implementation backs the site map with a Swing model). The sitemap sweep uses:

List<HttpRequestResponse>[] ref = new List[]{List.of()};
SwingUtilities.invokeAndWait(() -> ref[0] = api.siteMap().requestResponses());

This snapshots the site map on the EDT, then processes the snapshot off-EDT. The single-element array is used as a mutable carrier between the EDT lambda and the background thread (Java lambdas cannot capture non-final local variables).

13. SecretFinding Record & AuditIssue Builder

The data model for a finding and how it becomes a Burp AuditIssue.

Record Definition

record SecretFinding(
    String ruleId,        // e.g. "GITHUB_PAT_001"
    String ruleName,      // e.g. "GitHub PAT (Classic)"
    String keyName,       // e.g. "github_pat_classic"
    String matchedValue,  // actual secret (truncated >80 chars)
    String severity,      // HIGH / MEDIUM / LOW / INFORMATION
    String confidence,    // CERTAIN / FIRM / TENTATIVE
    int    lineNumber,    // 0-based newline count to match position
    String context,       // ±40 chars around match
    String sourceUrl,     // URL (may end with " [JS]", " [JSON]" etc.)
    String targetUrl      // bulk scan root URL; "" for proxy findings
)

AuditIssue Generation — Key Rules

  • Issue title: Always "[SecretSifter] Secrets / Credentials" — grouped by rule
  • No CRITICAL severity: Montoya API has no CRITICAL level; downgraded to HIGH
  • Grouped issue format: HTML table with all findings for the same rule at the same URL
  • Value truncation: Matched values >80 chars truncated to 77 + "…" in the detail display
  • Response markers: Byte-level highlighting of matched values — max 50 per issue, skip if response >4 MB, min value length 4 chars
  • 3-arg overload: toGroupedAuditIssue(group, rr, issueUrlOverride) — used by bulk scan to file issues at the target root URL (not the JS file URL) so they appear in the site map even when the JS file itself has no site-map entry

14. MCP Bridge (JSON-RPC Server)

How Claude Code and other MCP agents talk to Burp via SecretSifter.

  • Protocol: JSON-RPC 2.0 over raw TCP
  • Address: 127.0.0.1:8765 (loopback only — never exposed externally)
  • Auth: Bearer token in every request; token generated at first start, persisted to Burp Preferences, displayed in Settings UI with "Copy CLI Command" button
  • Threading: Thread-per-connection; fixed-size executor for request handling
  • Build: Full build only (secretsifter-mcp-*.jar). BApp Store build excludes the class entirely at build time.
  • Activation: Opt-in via Settings → MCP Bridge toggle. Not started on extension load by default.
  • Claude Code setup: claude mcp add secretsifter --transport http http://127.0.0.1:8765/mcp --header "Authorization: Bearer <TOKEN>"
  • Restart required: Claude Code must be restarted after claude mcp add — MCP servers are only loaded at session start
